# 專案規劃文件同步工作流程 (Planning Project Sync)

此 skill 用於**規劃設計階段**：把使用者與 Claude Code 討論出的結論（架構調整、Slice 拆分、技術選型變更等）回寫到本專案最高層的兩份規劃文件：

- [plan.md](../../plan.md)
- [execution-roadmap.md](../../execution-roadmap.md)

文件治理規則見 [CLAUDE.md](../../CLAUDE.md) 的「文件治理規則」章節。

---

## 強制要求：每次執行都必須先告知並確認

**在做任何修改之前**，必須先明確告知使用者：

> 「這個 skill 會更動本專案最高層的兩份文件：`plan.md` 與 `execution-roadmap.md`。請確認要修改的內容無誤後，我才會開始寫入。」

並列出「打算修改哪份文件、哪個章節、改成什麼內容」的具體摘要，**等待使用者明確同意（例如「好」、「確認」、「可以」）後才可執行寫入**。未取得確認前，不得呼叫 Edit/Write 修改這兩份文件。

---

## 執行步驟

### 步驟一：確認專案階段

先判斷專案目前處於哪個階段：

1. 檢查 `docs/architecture/adr/` 目錄是否已有 ADR 文件、`src/` 是否已有實際程式碼。
2. **若尚未開始實作（規劃設計期）**：正常執行步驟二～四。
3. **若已偵測到實作痕跡（例如已有 Slice 0 的程式碼或 ADR）**：依 CLAUDE.md 的治理規則，`plan.md` 與 `execution-roadmap.md` 不應再隨進度調整。此時應提醒使用者：
   - 這類進度變更建議改記錄在 `docs/architecture/adr/*`（ADR）或 Decision Log，而非修改這兩份頂層文件。
   - 詢問使用者是否仍要例外修改（例如範圍真的改變），若使用者堅持才繼續，並在文件中避免產生 `plan-v2.md` / `roadmap-new.md` 之類的分岔文件。

### 步驟二：整理討論結論

從當前對話中萃取出具體的變更點，區分要落在哪份文件：

- **plan.md**：屬於「北極星」等級的變動（定位、業務情境、整體架構、Phase 分類、技術選型總表、成功標準）
- **execution-roadmap.md**：屬於「執行路線」等級的變動（Slice 拆分、Slice 內容細節、執行節奏）

### 步驟三：呈現變更摘要並取得確認

依前述「強制要求」，列出摘要（修改哪份文件／哪個章節／改成什麼），等待使用者確認。

### 步驟四：套用修改

1. 使用 Edit 工具做**最小改動**，只動需要變更的章節，不做無關的格式美化。
2. **表格保護**：若修改的內容包含 Markdown 表格，必須保持原始格式，禁止為了視覺對齊增減 `|` 或 `-` 的數量。
3. **補 Changelog**：在被修改文件文末的 `## Changelog` 表格新增一行，欄位為「日期／修改章節／原因」。日期使用當天日期；「原因」用一句話說明本次討論結論的動機，不需要條列所有細節（細節已在文件本文）。
4. 修改完成後，簡短總結實際寫入了哪些變更（含 Changelog 新增的那一行）。

---

## 安全檢查與驗證

- **未確認不可寫入**：沒有取得使用者明確同意前，絕不呼叫 Edit/Write 修改 `plan.md` 或 `execution-roadmap.md`
- **實作期例外提醒**：偵測到專案已進入實作階段時，必須先提醒治理規則，而非直接修改
- **禁止分岔文件**：不得產生 `plan-v2.md`、`roadmap-new.md` 等替代檔案
- **語言規範**：文件內容遵循 CLAUDE.md 全域語言規則（繁體中文撰寫，技術術語保留英文並附中文解釋）
- **Changelog 不可略過**：只要實際寫入了 `plan.md` 或 `execution-roadmap.md`，就必須同步在該文件的 Changelog 補一行，不得只改本文不留紀錄

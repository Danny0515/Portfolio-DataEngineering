SHEET 01 · 兩個不同的工人

貨運工不管語言，翻譯員不管搬運

Kafka Connect 裡有兩種完全不同的工作，刻意設計成互不相關：貨運工（Connector）負責「東西怎麼搬」——去哪裡搬、搬到哪裡去；翻譯員（Converter）負責「東西怎麼寫」——用什麼格式描述這批貨。貨運工不在乎貨單用哪種語言寫，翻譯員也不在乎貨物從哪裡搬來。

SHEET 02 · 兩種倉庫規矩

自己開倉庫 vs 用代管倉庫

Kafka Connect 這個系統本身，允許把所有貨運工、翻譯員都放在同一個倉庫架上（plugin.path），要派工時現場自由配對——這是框架原生就有的彈性。但 MSK Connect（AWS 代管版）換了規矩：不開放你去架上自己拿，每一趟貨都得先把要用的貨運工跟翻譯員封裝成「一箱」，整箱交給它。

SHEET 03 · 這次真的踩到

先訂了兩箱，貨車只收一箱

項目 6 只需要驗證「箱子訂得出來」，所以分開訂了兩個獨立的小箱子——各自都順利驗收。項目 7 真的要叫貨車（aws_mskconnect_connector）來載的時候才發現：貨車的表單（CreateConnector API）上，「箱子」欄位只能填一個。兩個小箱子不能一起遞出去，得先拆開重新封成一箱。

✓ 項目 6：兩箱各自訂成 ACTIVE → ✗ 項目 7：貨車不收兩箱 → ✓ 重新封成合併版一箱，貨車收下、RUNNING
SHEET 04 · 以後怎麼辦

零件先分開放，需要時再組

現在只有一趟貨（一個 connector），手動封一箱沒問題。但以後貨運工、翻譯員的組合只會越來越多——業界的做法是把每個零件（每種貨運工、每種翻譯員）分開存放在同一個「零件庫」（S3），每次有新的一趟貨，用同一套「打包站」流程（Terraform）依這趟貨實際需要的零件現場組裝、封箱、送出去，而不是每趟貨都重寫一次打包邏輯。

城市與
工地

「環境要不要分帳號」跟「state 要不要拆開」，是兩條完全不同的分割線——答案常常也不一樣。

延續 docs/concepts/aws-network-eli5.html 的藍圖比喻——上一篇蓋的是一塊地，這篇拉遠鏡頭看整座城市怎麼規劃。

軸線一

先分城市

Dev、UAT、Prod 各自是一座獨立城市（AWS account）——自己的警察局（IAM）、自己的稅務局（帳單）。一座城市出事，燒不到隔壁城市。這才是「環境」原本要解決的問題。

軸線二

同一座城市，工地各自報批

同一座城市裡，不是每個建案都用同一張建照。長住大樓（Lakehouse）申請一張證，臨時工地（CDC 網路層）申請另一張——臨時工地要拆掉重蓋，不會連累旁邊已經蓋好的大樓。

為什麼不是

同張建照換裝潢，行不通

Terraform Workspace 聽起來像萬用解方——同一份設定，換個 workspace 就有獨立 state。但它的前提是「每個 workspace 蓋一模一樣的房子」，不是「這裡蓋大樓、那裡蓋工寮」這種本質不同的建案。

多帳號

整座城市分開，連地基都不共用

適合：dev/uat/prod 環境晉升

獨立資料夾（採用）

同城市，各自一張獨立建照，各自的圖紙

適合：同環境內、生命週期不同的建案

Workspace

同一張圖紙，只是貼了不同標籤

適合：每個 workspace 蓋一模一樣的房子
疊加

兩條線是疊加，不是二選一

真正的大公司通常兩條線一起用：先分城市（帳號分環境），每座城市裡再依生命週期拆工地（state 分 stack）。選了帳號分環境，不代表城市裡面就不用管 state 怎麼拆。

總結

總結

兩個不同軸線，各自對應不同的拆分需求。

軸線一：環境晉升（dev → uat → prod）——這題的業界做法是用不同 AWS account 分開，而不是同一個 account 裡用 Terraform workspace 切。理由是 blast radius：prod 出事不會波及 dev、IAM 權限天然隔離、帳單天然分開。AWS 官方的 Control Tower / Landing Zone 架構本身就是這個模式——而且這正是我們現在受它治理的那個組織帳號，也就是說「帳號分環境」這件事已經在更上層的組織層級發生了，只是不是這個專案自己在管。

軸線二：同一個環境內，基礎設施要不要拆成多組獨立 state——這是完全不同的問題，處理的是「即使只有一個環境，也不想把所有東西塞進同一個 Terraform state」，理由是 blast radius（同一個 state 裡，一次 destroy/apply 出錯波及範圍太大）、生命週期不同（有些資源長期存在、有些用完即拆）、或是團隊分工邊界。dev/ vs dev-slice2/ 就是這個軸線——它們都在同一個環境、同一個 AWS account 裡，只是因為生命週期不同（Slice 0/1 長期存在、Slice 2 用完即拆）而拆成兩組 state。
